## Smaller issues
- [x] README config section was missing the `tag_model` key (2026-10-26).
- [x] With `tag_model` set to a subclass, a base `UserTag` instance skipped the ownership check and became a tag named after its JSON, not a TypeError: models cast to string outside strict_types. Fixed on `read-side-features` by checking against the base class (2026-10-26).
- [x] Any other object in a tag array (say `attachUserTag([$post])`) was cast to its JSON and became a tag name. Values that cast to JSON (`Jsonable`), nested lists and `null` now throw `InvalidArgumentException`, alone or in a list; numbers and `Stringable` values stay tag names (2026-10-26).
- [x] `attachUserTag(['new name', $othersTag])` created `new name` in the caller's tags before the `TagNotOwnedException`, leaving an unattached tag. Every instance's owner is now checked before any name is created. Not a transaction around attach, which would add the `createOrFirst()` race two items down to attach (Mujahid, 2026-10-26).
- [x] `attachUserTag(['new name', $deletedOwnTag])`, with a stale instance of the caller's own deleted tag, created `new name` before the pivot's foreign key threw a `QueryException`. Attach now runs in a transaction like sync, which the next item's retry made safe (Mujahid, 2026-10-26).
- [x] `syncUserTags()` on MySQL/MariaDB threw `UniqueConstraintViolationException` when a concurrent request created the same new name: under REPEATABLE READ, `createOrFirst()`'s re-read uses the transaction's snapshot. Reproduced through the package in `ConcurrentRequestTest` on MySQL 9.7 and MariaDB 12.3; Postgres 17 passes. A real double submit also hits the pivot's unique index, and for an existing tag that failed on every database. Attach and sync now retry their transaction once on a unique violation when it is the outermost one. Ruled out: a shared-lock re-read (MariaDB 12.3's `innodb_snapshot_isolation` rejects it with 1020) and creating names before the transaction (tag index only, leaves names behind when sync fails) (Mujahid, 2026-10-26).
- [ ] Inside the app's own transaction, `attachUserTag()` and `syncUserTags()` on MySQL/MariaDB still throw `UniqueConstraintViolationException` when a concurrent request writes the same tag or attachment first, as 1.4.1 did: the snapshot is the caller's, so the package can't retry. The README doesn't say so. `DB::transaction($callback, $attempts)` won't retry it either: Laravel retries deadlocks and similar errors, not unique violations.
- [x] On MySQL/MariaDB, `résumé`/`resume`, `straße`/`strasse` and `🔥`/`🍕` merged into one tag (slug compared by collation). Fixed with a binary slug collation plus an upgrade migration in the README, and a MySQL CI job (2026-10-26).
- [x] Another user's tag ID from a request was a 500: the README now shows mapping `TagNotOwnedException` to a 404.
- [x] Postgres: `enforces unique slug per user constraint` failed in the full suite only, because Postgres aborts the wrapping transaction after the expected error. The duplicate insert now runs in a savepoint, and a Postgres 18 CI job runs the suite (2026-10-26).
- [x] MariaDB wasn't tested anywhere. A MariaDB 12.3 CI job now runs the suite on Laravel's `mariadb` driver, so the stub's `mariadb` branch runs; without the binary slug collation, four tests fail there (2026-10-26).
